## 1. Обзор

### 1.1. Что это

**MASCOT** (Multi-Agent System for Competency Optimization and Team distribution) —
мультиагентная система для:

- оценки компетенций сотрудников по данным из корпоративных систем
  (Git, Jira, LMS, HR, 1С);
- анализа требований проекта;
- подбора команды с обоснованием выбора;
- объяснения результата с указанием источников каждой оценки.

### 1.2. Зачем

`TODO: описать практическую задачу — что болит у заказчика, какие
процессы сейчас ручные, какую проблему решает система.`

Возможные направления для раскрытия:

- ручной подбор команды занимает N часов и субъективен;
- компетенции размазаны по системам, нет единого профиля;
- нет прозрачности: непонятно, почему выбрали именно этого человека;
- цифровой след используется как «чёрный ящик» без провенанса.

Возможные роли:

- **Тимлид / руководитель проекта** — подбирает команду;
- **HR / resource manager** — видит загрузку и компетенции;
- **Сотрудник** — видит свой профиль и обоснование оценок;
- **Аудитор / комплаенс** — проверяет, что система не нарушает 152-ФЗ
  и не принимает решения на основе единственной метрики.

## 2. Ключевые принципы

Проект строится на шести принципах, взятых из ТЗ. Каждый из них
**проверяем в коде и тестах**, а не просто декларируется.

### 2.1. Не использовать единственную метрику

**Что значит.** Одно число (например, «100 коммитов») не может быть
основанием для итоговой оценки. Оценка складывается из нескольких источников.

**Как реализовано.** `CompetencyAssessment` содержит `evidence: list[EvidenceSource]`.
Каждый источник вносит вклад, ни один не решает в одиночку.

**TODO: описать, как это будет проверяться в UI и API.**

### 2.2. Разделять наблюдаемые факты и аналитические выводы

**Что значит.** «87 коммитов» — факт. «Уровень Python = 0.8» — вывод.
В системе они хранятся **раздельно**.

**Как реализовано.**
- Факт: `Metric` (сырое число + источник + период + уверенность);
- Вывод: `CompetencyAssessment` (уровень + статус + evidence + rationale).

### 2.3. Учитывать период и достаточность данных

**Что значит.** «5 коммитов за неделю» и «5 коммитов за год» — разные вещи.
Если данных мало, вывод не делается.

**Как реализовано.** У каждой `Metric` есть `period_start`, `period_end`,
`sample_size`, `confidence`. Свойство `is_sufficient` проверяет пороги.

### 2.4. Выявлять противоречия между источниками

**Что значит.** Если HR говорит «senior», а Git показывает активность
джуна — это противоречие, и его надо **явно** зафиксировать, а не сгладить.

**Как реализовано.** `_detect_contradictions` в `skill_evaluator.py`
сравнивает заявленный уровень с подтверждённым. При разрыве ≥ 0.4 —
статус `CONTRADICTORY` + запись в `Contradiction`.

### 2.5. Назначать дополнительное тестирование при недостатке данных

**Что значит.** Если по сотруднику мало данных — система не гадает,
а просит проверить.

**Как реализовано.** `CompetencyAssessment.follow_up: list[str]` —
список конкретных рекомендаций (что проверить, зачем).

### 2.6. Обеспечивать объяснимость и фиксировать происхождение

**Что значит.** Любая рекомендация отвечает на «почему» и «откуда данные».

**Как реализовано.**
- `Metric` фиксирует провенанс для каждой метрики;
- `TeamDecisionReport.explanation` — текстовое обоснование;
- `TeamDecisionReport.requirement_coverages` — структурированное покрытие.

## 3. Архитектура: четыре слоя и ядро

### 3.1. Общая схема

```
┌─────────────────────────────────────────────────────────────┐
│                     Ядро MAS (core/)                        │
│  AgentMessage · MessageBus · BaseAgent · Registry           │
└─────────────────────────────────────────────────────────────┘
          ↕                  ↕                  ↕
┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
│   Слой данных    │→│  Аналитический   │→│  Слой решений    │
│  (data_layer)    │ │  (analytics)     │ │  (decision)      │
└──────────────────┘ └──────────────────┘ └──────────────────┘
                                                  ↓
                                       ┌──────────────────────┐
                                       │   Слой доверия       │
                                       │   (trust_layer)      │
                                       └──────────────────────┘
```

Слои соединены **последовательно**: каждый следующий использует
результат предыдущего. Такая схема обеспечивает прослеживаемость:
рекомендация в итоге опирается на конкретные метрики с известным
происхождением.

### 3.2. Слои

| Слой | Отвечает за | Результат |
|---|---|---|
| **Данные** | Сбор, парсинг, валидация, дедупликация цифрового следа | Нормализованный JSON о сотруднике |
| **Аналитика** | Оценка компетенций, бенчмаркинг, маппинг на требования | `EmployeeEvaluation` с провенансом |
| **Решения** | Подбор команды, расчёт покрытия, оценка рисков | `TeamDecisionReport` |
| **Доверие** | Объяснения, guardrails, провенанс, аудит | Текстовое и структурированное объяснение |

### ADR-001: Pydantic вместо dataclass для доменных моделей

**Решение.** `Employee`, `Project`, `TeamRecommendation` — на Pydantic v2.

**Причина.** Единый механизм валидации на границе (JSON → модель),
сериализация для API и шины из коробки.

**Последствия.** Небольшой overhead на создание объектов. Компенсируется
надёжностью.

`TODO: описать, где dataclass всё ещё уместен (например, Metric внутри).`

### ADR-002: Шкала 0.0 – 1.0

**Решение.** Все уровни навыков и требований — `float` в диапазоне 0–1.

**Причина.** `TODO: твоё обоснование.`

### ADR-003: Разделение фактов и выводов

**Решение.** `Metric` — факт, `CompetencyAssessment` — вывод.

**Причина.** Правило из ТЗ + возможность отследить провенанс.

### ADR-004: Детерминированный оценщик первым

**Решение.** Сначала `skill_evaluator.py` (скрипт), потом LLM-обёртка.

**Причина.** Тесты и логика работают без сети и без затрат на LLM.
LLM добавляется как **ещё один источник свидетельств**, а не как
замена логике.
